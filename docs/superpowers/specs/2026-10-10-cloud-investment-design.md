# 클라우드 신규 투자 운용: Claude 구독 + JEV

작성일: 2026-10-10 Asia/Seoul. 상태: 사용자 구현·인증 설정 승인, 구현 진행 중. 인증 성공·예약 재개는 별도 실제 확인이 필요함.

## 사용자가 요청한 결과

신규 투자 운용을 Mac 예약에서 클라우드로 이전한다. Mac과 Codex 앱이 꺼져 있어도 조사·수집·검토·승인·정규장 모의 체결을 수행하고 Chrome 창을 열지 않는다. 기존 Claude 구독과 연결된 JEV API를 모두 사용한다. 수집과 검토 시간을 분리하고 수집 종료 후 최대30분, 최대5회 검토, 승인 증명15분 유효기간을 보존한다. 실제 증권 주문을 추가하지 않는다.

## 확인한 현재 상태

- 기존 소유자 전용 Sites 프로젝트는 버전31, Claude 검토 configured/required true, maxMinutes30이다. 서버 자동 운용 enabled true이고 sessionMode true다.
- Mac 신규 투자 예약 `committee-lab-mac`, `committee-lab-mac-2`는 PAUSED다. 클라우드 한국·일본 위험 예약은 활성, 미국 위험 예약은 중지다.
- 클라우드 updater에는 Mac 검토 스크립트가 없어 `macReviewerRequired`로 신규 활동을 보류한다. 현재 서명자는 Mac의 개인키를 사용한다.
- GitHub CLI가 `fdo2a` 계정에 인증되어 있다. `fdo2a/committee`는 공개 저장소이고 워크플로가 없다. 이 공개 저장소를 private Site 코드·계좌·인증의 업로드 대상으로 사용하지 않는다.
- JEV는 기존 미국 discovery/admission 비교 평가다. 원본 후보 전체를 평가하되 독립적인 선정·비중·Claude 승인·위험 한도를 변경하지 않는다. API 키는 이미 서버에서 관리한다.

## 선택한 구성

기존 Sites 시장별 클라우드 예약을 조사·운용 주체로 재사용하고 비공개 GitHub Actions를 Claude 전용 검토기로 연결한다. Sites 예약은 조사·원문 읽기·부분 조사 저장·전체 테마 가격 수집·JEV 평가·검토 요청·반려 보완·운용 제출을 수행한다. GitHub 작업은 명령행 Claude Code를 구독 OAuth 인증으로 실행하고 승인된 정확한 요청만 서명한다. 조사와 검토는 별도 실행 주체이며 모델이 계좌를 직접 쓰지 않는다.

Claude 유료 API로 자동 전환하지 않는다. JEV는 기존 명시적 유료 API 범위를 사용한다. GitHub 실행 시간은 별도 한도가 있으므로 무료 한도와 초과 과금 설정을 확인하고, 초과 결제를 자동 활성화하지 않는다. GitHub 장애·실행 지연·Claude 구독 한도 초과 시 신규 활동을 보류하고 기존 위험 점검을 계속한다.

JEV를 Claude 논리 검토의 승인 대체물로 사용하는 안은 채택하지 않는다. JEV의 점수·확신은 기존 역할에 따라 조사 비교에 사용하며, 승인 문장이나 수익률 확률로 바꾸지 않는다. 지역 확대와 JEV 결과에 따른 선정 변경은 이 이전 작업에 포함하지 않는다.

## 실행 흐름

1. 기존 클라우드 예약이 Sites 도구로 현재 서비스 인증을 얻고 시장·세션·revision·계좌 일시정지를 확인한다. 서비스 인증을 모델 텍스트·파일·로그에 넣지 않는다.
2. 장전에는 출처 있는 컨셉과 원본 후보 전체를 보존한다. 미국은 기존 JEV discovery/admission 순서를 사용하고 평가 후 최신 revision을 읽는다. 한국·일본과 개장·마감에는 기존 JEV 호출 제한을 유지한다.
3. 기존 updater가 전체 테마 후보와 기존·보유·승인 종목을 합산해 실제 가격을 수집한다. 위험 처리를 먼저 수행하고 재무·ETF 수집까지 끝난 뒤 하나의 reviewWindow를 시작한다.
4. 클라우드 브리지가 exact payload·context·scope·codeDigest·reviewWindow·round를 서버 검토 대기열에 등록한다. 같은 요청 해시는 같은 작업을 재사용한다. 대기열 등록은 주문이나 계좌 state를 바꾸지 않는다.
5. 서버는 해당 비공개 저장소의 GitHub workflow_dispatch를 요청한다. 전용 최소 권한 GitHub 인증을 서버 secret에 보관한다. 작업 ID만 전달하고 payload·서비스 인증·서명키를 dispatch 입력에 넣지 않는다. 중복 dispatch를 방지하고 실패 시 명시적으로 보류한다.
6. GitHub 작업은 service-access secret으로 같은 Site의 해당 작업을 읽고 revision·scope·원본 해시·코드 버전·기한을 검증한다. redirect로 서비스 인증을 전달하지 않는다. 검토용 입력은 기존 전체 해시 결합 요약과480,000 UTF-8 바이트 상한을 재사용한다.
7. Claude는 제한된 도구 없는 별도 세션에서 논리만 검토한다. 서비스 인증·서명키·GitHub 인증을 Claude 모델 입력이나 하위 프로세스 환경에 제공하지 않는다. 구독 OAuth는 Claude CLI 인증 용도로만 전달한다.
8. 반려 시 구조화된 issues를 대기열에 기록한다. 기존 클라우드 조사 주체가 원문 근거로 research/decision만 보완한다. 가격·재무·시각·시장·단계·revision·위험 기준은 변경할 수 없다. 같은 reviewWindow와 최대5회 한도를 유지한다. 근거를 보완할 수 없으면 지적된 종목을 빼거나 비중을 줄이고, 논지가 무너졌거나 남은 종목이 2개 미만일 때만 watch/held다(2026-10-28 사용자 지시, 2026-10-08 명세 참조).
9. 명시적인 깨끗한 승인에만 클라우드 전용 개인키로15분 유효한 증명을 생성한다. 요청 본문·scope·codeDigest·revision·발급/만료 시각을 기존 계약으로 결합한다. 서버는 등록된 클라우드 공개키로 이를 검증한다. 기존 Mac 코드 빌드 승인용 개인키를 클라우드로 이동하지 않는다.
10. 클라우드 updater는 반환된 증명과 불변 필드를 검증한 뒤 기존 운용 API에 제출한다.409이면 증명을 재사용하지 않고 원래 reviewWindow 안에서 최신 계좌로 재심사한다. 저장 결과를 readback해 조사 저장·승인·체결·보류를 구분한다.

## 데이터·인증 경계

검토 대기열은 계좌 state와 별도 저장소에 둔다. opaque 작업 ID, canonical request hash, payload/context, deadline, revision, scope, codeDigest, round, pending/running/approved/rejected/expired/error 상태와 검토 결과를 저장한다. queue에 source/서비스 토큰·OAuth·서명키를 저장하지 않는다. 최대10MB 요청과30분 deadline을 서버에서 검증한다. 만료된 원본과 결과는 정리하며 저장 보존 정책을 구현 계획에서 확정한다.

GitHub 저장소는 새 비공개 저장소를 사용한다. 필요한 실행 스크립트와 승인된 소스만 동기화하며 `.env`, `.review`, 인증 파일, 계좌 스냅샷, 개인키, 임시 가격 파일은 커밋하지 않는다. 모델·워크플로의 원문 출력과 shell tracing은 끈다. GitHub 결과 로그에는 작업 ID·단계·성공/보류와 credential-free 오류 코드만 남긴다.

최초1회 필요한 설정은 다음과 같다.

- Claude 구독용 장기 OAuth 인증. 공식 `claude setup-token` 흐름을 사용하며 기존 로그인 파일을 읽어 인증을 추출하지 않는다. 브라우저 자동 실행은 하지 않고 사용자가 필요한 최초 인증을 선택해 수행한다.
- 비공개 저장소의 workflow_dispatch에만 필요한 GitHub 최소 권한 인증. 현재 CLI의 광범위 OAuth를 서버 secret으로 복사하지 않는다.
- GitHub Secrets: Claude 구독 OAuth, 해당 Site 서비스 접근 인증, 새 클라우드 전용 서명키. 값은 숨긴 stdin/환경과 native secret 설정으로만 전달한다.
- Site Secrets: GitHub 최소 권한 인증, 비공개 저장소 식별자, 클라우드 검토 공개키. JEV 키와 기존 환경 변수·접근 권한은 보존한다.

처음 받은 Site 서비스 접근 인증이 GitHub에서도 유효함을 같은 Site origin의 읽기 전용 호출로 확인한다. 인증 만료·회전이 발견되면 신규 투자를 보류하고 재설정을 요청한다. 외부 접근 정책을 public으로 바꿔 해결하지 않는다.

## 시간과 예약

기존 한국·일본08:00/09:20/16:00 Asia/Seoul과 미국08:30/09:50/16:30 America/New_York를 유지한다. 뉴욕 DST와 미국 금요일 마감의 한국 토요일 실행을 보존한다. 장전 신규 판단, 개장 위험 관리, 마감 장전 승인 주문의 확정 종가 모의 편입을 유지한다.

GitHub Actions 지연도 수집 후30분 reviewWindow에 포함한다. 시장 단계 종료가 더 빠르면 해당 기한을 따른다. 수집 중 단계가 바뀌면 신규 승인만 보류하고 위험 전용 처리는 현재 단계에서 이어간다. 과거 시가·종가로 소급 승인/체결하지 않는다.

Mac 신규 투자 예약은 계속 PAUSED로 유지한다. cloud 경로의 실제 인증·검토·서명·API 검증이 끝난 뒤 기존 시장별 클라우드 예약 둘을 신규 투자 역할로 변경하고 사용자의 재개 지시에 따라 활성화한다. 이전4시간 예약·주간 보고 예약·일회성 배포 재개 예약은 변경하지 않는다. 중복 시장 예약을 만들지 않는다.

## 검증과 전환 기준

- 대기열 등록/조회/결과 저장은 계좌 state·주문·현금·체결을 바꾸지 않는다.
- 모델/서명 프로세스에 불필요한 인증이 전달되지 않는 테스트와 redirect 거부 검사가 통과한다.
- 서명 변조·payload/scope/revision/codeDigest 변경·15분 만료·30분 deadline 변경·6회차 검토·중복 결과 저장·409 증명 재사용을 거부한다.
- 요청 크기 초과·GitHub 오류/지연·Claude 인증/구독 한도·잘못된 JSON·반려·근거 부족은 신규 활동만 보류하고 위험 처리는 유지한다.
- JEV가 기존 shadow 범위와 원본 후보 전체·paid opt-in·중복 결제 방지·실패 기록·최신 revision 계약을 유지한다.
- 실제 Claude 코드 심사와 보호된 빌드 후 동일 해시를 기존 비공개 Site에 배포한다.
- 실제 클라우드 작업에서 Claude 구독 인증과 전용 서명을 검증하되 계좌 쓰기/신규 매매를 테스트 자료로 사용하지 않는다.
- 클라우드 예약의 저장된 프롬프트·시간·활성 상태를 native 도구로 확인한다. 예약 활성화만으로 실제 투자 승인/체결 완료라고 보고하지 않는다.

## 남은 외부 설정

현재 Claude 구독용 클라우드 OAuth와 최소 권한 GitHub dispatch 인증은 등록되어 있지 않다. 이 두 인증 없이는 클라우드 검토의 성공을 확인하거나 신규 투자 예약을 재개할 수 없다. 코드 구현 전에 인증 제공 경로와 GitHub 무료 실행 한도·과금 차단을 확정한다. Chrome을 자동으로 열어 이 설정을 진행하지 않는다.

## 사용자 승인에 따른 후속 요구사항, 2026-10-10 및 2026-10-12

기본 규칙은 계속 Claude 승인·정확한 요청 서명·15분 증명·서버 재검증이다. 사용자는 2026-10-10 기존 예약의 다음 적격 시장/거래일 1회(주식·ETF 장전·개장·마감)에만 Claude 투자 심사를 생략하는 명시적 운영자 예외를 승인했다. 이는 Claude 승인 증명이 아니며 예외 상태와 실제 데이터·재무·위험·정규장 체결 검사를 별도로 기록한다. 서버의 OPERATOR_REVIEW_EXCEPTION이 첫 유효 쓰기에서 시장/현지 날짜를 고정하고, 완료한 범위를 재개하지 않으며 실패했어도 현지 자정에 만료한다. 다른 시장/날짜의 두 번째 운용은 허용하지 않는다. 모델 인증 실패를 이 예외로 바꾸거나 클라우드 검토 큐를 자동 활성화하지 않는다.

확인한 사용자 승인 기록: Codex 채팅 `01a11f38-5213-79a2-be31-b545b5e6800f`, 사용자 메시지 `01a12634-411e-7c63-a69c-4675db38f8ea`. 당시 제시한 범위는 “다음 유효한 시장의 운용 1회(주식·ETF의 장전·개장·마감)”이며, 예외 기능의 코드 빌드·배포도 그때 한 번만 승인 없이 진행할지 물은 데 대해 사용자는 “이번 예외 기능의 빌드·배포도 승인 생략”이라고 답했다. 과거 1회 빌드 예외는 이미 Site35에 사용됐다. 이번 변경과 이후 코드 빌드·배포에는 적용하지 않는다. 현재 코드 심사는 앱에서 읽은 이 사용자 메시지 원문을 심사 대상 소스와 분리한 `userAuthorization` 필드로 함께 제공한다. 문서가 자체적으로 승인 권한을 발급하지 않는다.
